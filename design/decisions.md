## 2026-10-18

| # | Decision | Source |
|---|---|---|
| T8 | **Supabase is the data and timing layer, and Vercel runs all the code.** Supabase `pg_cron` calls the app's round engine on a schedule (see T9), replacing Vercel Workflow and Vercel Cron. The work stays in the Next.js app rather than Supabase Edge Functions, so there's one runtime and one deploy. The owner handles Supabase's inactivity pause by upgrading or scheduling a keep-alive if needed. | Owner, refining Claude's proposal |
| T9 | The round engine runs **once a day at 8 a.m. Eastern** (12:00 UTC), not every 15 minutes. Every step in a round is measured in days, user actions and webhooks act right away, and a morning run means messages always arrive at a sensible hour. Failed steps retry the next day. | Owner |
| T10 | **Lean repo layout.** pnpm workspaces without Turborepo. One shared package (`packages/core`) for business rules and shared types. Migrations live in `supabase/`, where the Supabase CLI expects them, and AI code lives in `apps/web/lib/ai`. Tools or packages are added only when there's a real need. | Owner, on Claude's recommendation |
| T11 | **The AI backend is replaceable.** Calls go through the AI SDK and Vercel AI Gateway, with usage billed through Vercel and no separate AI provider account. The model for each task is set in one config file. The design talks about "the AI model" rather than a vendor, and Claude Opus 5.5 is today's default. Switching to a cheaper model or another provider such as OpenAI should be a config change, and web search sits behind a replaceable step. | Owner |
| T12 | **Push notifications: decision deferred** (revisits D15). The MVP builds email first, and the notification service sends through a channel list so push can be added without rework. Push is its own optional ticket (W5-4, about 1–2 days), decided before Wave 5. | Owner |
| T13 | **Inbound email quick capture stays in the MVP** (W4-3), including the "Who is this about?" reply. | Owner |
| T14 | **Simpler round statuses: 9 instead of 11.** `purchasing` is dropped, because the `orders` table already tracks each order's progress and approval goes straight to `ordered`. `reaction_pending` is merged into `delivered`. §5 shows one main path plus three side statuses. | Owner, on Claude's recommendation |
| T15 | **Look and feel is settled before screens are built.** A new Wave 1 ticket (W1-7, ALL-41) picks the UI kit (Tailwind plus shadcn/ui by default, shared with the extension), defines a style guide as tokens, and produces clickable mock-ups of the key screens for the owner and Jim to sign off. W2-1 and the other screen tickets depend on it. | Owner, on Claude's recommendation |

## 2026-10-25

| # | Decision | Source |
|---|---|---|
| T19 | **One app, one account, one repo for the whole platform, built to split later.** Scan-to-gift, gift lists and the concierge always feel like one app to users: a progression from quick one-off use to the deep concierge. One Next.js app, one sign-in and user record, one shared `people` record that can later link to a user's own account, and one repo (gifts-af, renamed to the platform name once chosen). **Guardrails against one-way doors:** a Postgres schema and a code module per product, with no reaching into another product's tables or internals (checked by lint); a path per product; the concierge's money and sensitive data stay inside it (D31); every printed QR code goes through our own short link, and nothing is printed until the name and domain are settled. Jim's list app moves into the repo when ready. Design §2.2. | Owner, on Claude's recommendation |
| T20 | **GiftsAF becomes the starting point of the platform app** (refines T19). Its Next.js app, Supabase sign-in, shadcn/ui setup and Vitest tests become `apps/web` in this repo, keeping its git history, instead of building the scaffold from scratch. How **[Claude's call]**: (1) **whenever it's ready**, with a short code freeze agreed with Jim (there's no external deadline; the Nov 1 soft launch was only an aspirational date); (2) GiftsAF's history is imported as `apps/web`, and the GiftsAF repo is archived with a pointer here; (3) its Vercel project (`gift-me`, in the "GiftMe" team) and Supabase project become the platform's production ones, re-pointed at this repo with root `apps/web`, keeping its domain, env vars and Supabase integration, plus a new Supabase `dev` project; (4) its tables move from `public` to a `lists` schema in a migration (3 users, low risk); (5) its email-and-password accounts stay, and Google sign-in is added in W2-1 for contacts import; (6) its list code moves into `modules/lists`, while sign-in, layout and Supabase clients become shared. Schema and core logic work (W1-5) can start before the move, against local Supabase. | Owner (go); details Claude's recommendation, to confirm with Jim |
| T21 | **The repo is renamed `gifts-af/gift-me`** (was `gift-concierge`, briefly `gifts-af`). It holds the whole platform. `gift-concierge` read as if lists belonged to the concierge, and `gifts-af/gifts-af` was redundant. Products keep descriptive code names (`modules/lists`, `modules/concierge`), and public names live only in what users see, so a brand change (ALL-14: "GiftMe" is taken) touches only visible text. GitHub redirects old URLs. | Owner |
| T22 | **A daily keep-alive stops the free Supabase project from pausing** (follows up T8). Free projects pause after about 7 days without database activity, which broke deploys on 2026-10-25. A Vercel Cron job calls `/api/keepalive` once a day; the route checks `CRON_SECRET` and runs one tiny query. This uses Vercel Cron rather than Supabase `pg_cron` (T8), because a paused database can't wake itself. A GitHub Actions schedule was ruled out, since GitHub turns off schedules in repos that go quiet for 60 days. Upgrade to Supabase Pro ($25/month, no pausing) once real users depend on the app. ALL-43. | Owner, on Claude's recommendation |
| T23 | **No hard-coded values: fees, limits and timings are settings, not code.** It started with Zinc's order fee, which Zinc sets and can change without us. The owner then made it the default for everything: avoid hard-coding (CLAUDE.md > Code). `packages/core` holds no business numbers. The budget functions take `feeCents`, and the schedule functions take a `ScheduleSettings` object (planning delivery days, safety buffer, round lead time, reminder timings, fastest shipping). Both are required inputs with no built-in defaults. The values live in `concierge.app_settings` rows (`zinc_order_fee_cents` 100, and the §4.1 schedule values), which the server code that calls core reads. Changing one is a data change with no deploy, and once card payments arrive (T16), each funding mode can have its own fee row. Each order also records the fee Zinc actually charged, in `orders.fee_cents`. Per-user values stay in `profiles` (`over_budget_pct`). Only true constants, such as holiday dates and calendar math, stay in code. ALL-19. | Owner; storage on Claude's recommendation |
