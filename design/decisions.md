| T26 | **How schema v1 is laid out** (ALL-19, refines §3). (1) **Money settings live in the concierge.** The shared `public.profiles` keeps only display name, email, phone and timezone. Over-budget %, notification preferences, funding mode and the Zinc connection go in a per-user `concierge.accounts` table, so money details stay inside the concierge (D31). Zinc keys are stored in Supabase Vault, and `accounts` keeps only their secret ids. (2) **Every user-owned row carries `user_id`**, including rows that belong to a round (ideas, orders, reactions), so one privacy rule (`user_id = auth.uid()`) covers every table. (3) **Links between rows include the owner.** A child references its parent by `(id, user_id)` together, so a row can never point at another user's person or round; plain RLS doesn't stop that, because foreign-key checks ignore it. (4) **A profile is created at sign-up** by a trigger, and existing accounts are backfilled, taking the display name from sign-up. (5) **Who writes what.** Users write their own setup: people, occasions, budgets, facts, answers and captures, plus their name, timezone and over-budget %. That way, budget checks and status moves in `packages/core` can't be skipped, and nobody can point their account at someone else's stored Zinc key. (6) **One live order per idea** (a unique index ignoring failed, cancelled and refunded orders), so a retry can't buy twice, and an order or rejection must name an idea from its own round. (7) **Functions are not callable by default.** A new function must be granted on purpose, so server-only ones can't be reached through the API. (9) The list tables' move into a `lists` schema is part 2b, after the `dev` project exists (ALL-39). | Owner, on Claude's recommendation |
| T27 | **Deletes are soft; hard deletes are an admin action** (refines C-7). Deleting a person or occasion in the app sets `deleted_at` instead of removing the row, so gift and order history survive. Users can't hard-delete those rows; they call `public.delete_person` or `concierge.delete_occasion`, and the privacy rule hides deleted rows from them. When a person or occasion is deleted, a trigger skips its open rounds right away (anything not yet ordered), and no new round can start for it, so nothing is ever bought for someone who was deleted. Ordered and delivered rounds are left alone. Smaller items (budgets, single facts, questions, captures) keep normal deletes, because nothing hangs off them. **Removing data for real**, for example a GDPR erasure request, uses `admin.hard_delete_person` or `admin.hard_delete_account`. These live in a private `admin` schema that only the server can run, remove every row (including order history), and log the kind, target id, owner id, who asked and why in `admin.deletion_log`, with ids only and never the deleted data. An admin screen for these comes with the privacy pass (ALL-37); until then an admin runs them from the Supabase SQL editor as allensforever711. Capture screenshots in Storage must also be removed by the server when hard-deleting. ALL-19. | Owner (soft deletes and an admin hard delete); details on Claude's recommendation |
