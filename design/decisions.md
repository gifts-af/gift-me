| T22 | **A daily keep-alive stops the free Supabase project from pausing** (follows up T8). Free projects pause after about 7 days without database activity, which broke deploys on 2026-10-25. A Vercel Cron job calls `/api/keepalive` once a day; the route checks `CRON_SECRET` and runs one tiny query. This uses Vercel Cron rather than Supabase `pg_cron` (T8), because a paused database can't wake itself. A GitHub Actions schedule was ruled out, since GitHub turns off schedules in repos that go quiet for 60 days. Upgrade to Supabase Pro ($25/month, no pausing) once real users depend on the app. ALL-43. | Owner, on Claude's recommendation |
| T23 | **No hard-coded values: fees, limits and timings are settings, not code.** It started with Zinc's order fee, which Zinc sets and can change without us. The owner then made it the default for everything: avoid hard-coding (CLAUDE.md > Code). `packages/core` holds no business numbers. The budget functions take `feeCents`, and the schedule functions take a `ScheduleSettings` object (planning delivery days, safety buffer, round lead time, reminder timings, fastest shipping). Both are required inputs with no built-in defaults. The values live in `concierge.app_settings` rows (`zinc_order_fee_cents` 100, and the §4.1 schedule values), which the server code that calls core reads. Changing one is a data change with no deploy, and once card payments arrive (T16), each funding mode can have its own fee row. Each order also records the fee Zinc actually charged, in `orders.fee_cents`. Per-user values stay in `concierge.accounts` (`over_budget_pct`, T25). Only true constants, such as holiday dates and calendar math, stay in code. ALL-19. | Owner; storage on Claude's recommendation |
| T24 | **Vercel stays on Hobby while we're developing and testing** (closes the W1-6 Hobby-or-Pro question). Hobby's terms are for non-commercial use, which fits until real users pay or depend on the app. Move to Pro ($20 a month) before a commercial launch, or sooner if idea generation (about 40–60 s, W1-3) hits Hobby's function time limit **[Verify when W3 builds idea generation]**. The AI Gateway spending cap and alerts are already set (design §7). Environments: Supabase `dev` (`gift-me-dev`) serves local and preview builds, and `prod` serves Production only (README > Environments). ALL-39. | Owner |
| T25 | **How schema v1 is laid out** (ALL-19, refines §3). (1) **Money settings live in the concierge.** The shared `public.profiles` keeps only display name, email, phone and timezone. Over-budget %, notification preferences, funding mode and the Zinc connection go in a per-user `concierge.accounts` table, so money details stay inside the concierge (D31). Zinc keys are stored in Supabase Vault, and `accounts` keeps only their secret ids. (2) **Every user-owned row carries `user_id`**, including rows that belong to a round (ideas, orders, reactions), so one privacy rule (`user_id = auth.uid()`) covers every table. (3) **Links between rows include the owner.** A child references its parent by `(id, user_id)` together, so a row can never point at another user's person or round; plain RLS doesn't stop that, because foreign-key checks ignore it. (4) **A profile is created at sign-up** by a trigger, and existing accounts are backfilled, taking the display name from sign-up. The profile's email always mirrors the account's (users can't edit it, since messages go to it), and timezone starts unknown rather than assumed. (5) **Who writes what.** Users write their own setup: people, occasions, budgets, facts, answers and captures, plus their name, timezone and over-budget %. The server (service role) writes everything else: rounds and everything on them (ideas, rejections, orders, reactions, notifications, inbound mail), the funding mode and Zinc connection, and `people.linked_user_id`. That way, budget checks and status moves in `packages/core` can't be skipped, and nobody can point their account at someone else's stored Zinc key. (6) **One live order per idea** (a unique index ignoring failed, cancelled and refunded orders), so a retry can't buy twice, and an order or rejection must name an idea from its own round. (7) **Functions are not callable by default.** A new function must be granted on purpose, so server-only ones can't be reached through the API. (8) Round status is a Postgres enum, matching `ROUND_STATUSES` (a test checks it); other statuses are text with a check, which is easier to change. Limits set by vendors, such as Zinc's 240-character gift message, are app settings checked by the server (T23). (9) The list tables' move into a `lists` schema is part 2b, after the `dev` project exists (ALL-39). | Owner, on Claude's recommendation |
| T26 | **Deletes are soft; hard deletes are an admin action** (refines C-7). Deleting a person or occasion in the app sets `deleted_at` instead of removing the row, so gift and order history survive. Users can't hard-delete those rows; they call `public.delete_person` or `concierge.delete_occasion`, and the privacy rule hides deleted rows from them. When a person or occasion is deleted, a trigger skips its open rounds right away (anything not yet ordered), and no new round can start for it, so nothing is ever bought for someone who was deleted. Ordered and delivered rounds are left alone. Smaller items (budgets, single facts, questions, captures) keep normal deletes, because nothing hangs off them. **Removing data for real**, for example a GDPR erasure request, uses `admin.hard_delete_person` or `admin.hard_delete_account`. These live in a private `admin` schema that only the server can run, remove every row (including order history), and log the kind, target id, owner id, who asked and why in `admin.deletion_log`, with ids only and never the deleted data. An admin screen for these comes with the privacy pass (ALL-37); until then an admin runs them from the Supabase SQL editor as allensforever711. Capture screenshots in Storage must also be removed by the server when hard-deleting. ALL-19. | Owner (soft deletes and an admin hard delete); details on Claude's recommendation |
